# IBM Bob in qlab — Integration Options and Connection Points

**Status:** analysis and marked seams. Lane A is wired (`.bob/mcp.json`); lanes
B–D are documented, not built.

**Goal:** make IBM Bob a real, load-bearing part of qlab without changing one
line of the workforce, the referee gate, or the execution path.

**Constraint that drives every choice below:** qlab's governance is enforced by
deterministic code, not by whichever model is driving. Bob must therefore enter
qlab as a *client of the governed surface*, never as a new authority inside it.
Any lane that would give Bob its own path to the registry, the book, or the
referee is rejected on invariants 1 and 3 regardless of how convenient it is.

## What IBM Bob actually is

Bob is IBM's agentic SDLC environment. Two shipping surfaces matter here:

| Surface | What it is | Relevance to qlab |
|---|---|---|
| **Bob IDE** | Standalone AI-native IDE with Ask / Plan / Agent modes, custom modes, skills, rules | Operator and developer seat |
| **Bob Shell** | Terminal agent; `bob -p` runs non-interactive for scripts and CI (API-key auth, not IBMid) | Structural analogue of the `claude` CLI the workforce already drives |

Bob's project-level extension points, all under `.bob/`:

| Artifact | Purpose | Verified |
|---|---|---|
| `.bob/mcp.json` | MCP servers — `mcpServers` map, stdio / `streamable-http` / sse, `alwaysAllow`, `disabled`; project config wins over `~/.bob/mcp.json` | Documented |
| `.bob/custom_modes.yaml` | Custom modes: role definition + instructions + a deterministic set of permitted tools | Documented; exact key names need confirming against a live install |
| `.bob/skills/<name>/SKILL.md` | Agent Skills — frontmatter `name` + `description`, description drives activation | Documented |
| `.bob/rules/` | Persistent rules applied across every conversation and mode | Documented |
| `AGENTS.md` (repo root) | Project context Bob's `/init` generates and reads | Documented; **qlab already has one** |

Built-in mode tool groups are `Read`, `Edit`, `Execute`, `MCP`, `Skill`, `Todo`,
`Subtask`, `Subagent`, `Mode`. That list is the single most useful fact for
qlab: a mode granted **`MCP` only** has no filesystem, no editor, and no shell —
which is exactly the boundary qlab's role definitions already assert.

## Where qlab stands today

- `.bob/personas/*.yaml` exists and is generated by `_write_bob` in
  [loader.py:132](qlab/agents/loader.py:132). **It is a neutral projection, not a
  format Bob loads.** `persona:` / `allowed_tools:` / `system_prompt:` are
  qlab's own keys. It proves the one-source org chart can target a second
  orchestrator; it does not yet make Bob run the desk. Worth stating plainly in
  any submission rather than implying a live integration.
- `AGENTS.md` at the repo root is Bob's native context file and is already
  present — though it currently carries a bad find-and-replace (`.Codex/agents/`,
  "Codex workforce") from an earlier rename.
- `qlab/mcp/tui_proxy.py` is a stdio MCP server that never opens DuckDB and
  whose authority is capped at observation, research, workforce coordination,
  and *dry* rebalance previews. **This is the natural Bob attachment point** and
  needs no new code to serve one.
- `record_invocation(..., backend="claude_cli")` in
  [model_routing.py:93](qlab/operator/model_routing.py:93) already carries a
  `backend` column, so a Bob-served phase is auditable the day it exists.

## The four lanes

### Lane A — Bob as an MCP client of the governed desk ✅ wired

`.bob/mcp.json` points Bob at `python -m qlab.mcp.tui_proxy`. Bob becomes another
operator surface beside the TUI and the web client: it can read the portfolio,
the regime panel, the audit trail and the research runs, and it can request a
*dry* rebalance preview — and nothing else, because that is all the proxy
exposes.

- **Disruption:** none. One additive config file. No qlab code reads it; the
  proxy cannot tell a Bob client from a Claude one.
- **Governance fit:** excellent. `alwaysAllow` is listed for observation tools
  only, so every tool that persists a decision, starts a workflow, or previews a
  plan stops for a human click in Bob's own approval UI. Bob's approval model
  and qlab's mandate reinforce each other instead of competing.
- **Prerequisite:** an owner runtime must be up (`qlab tui` or `qlab ui`), since
  the proxy is HTTP-only by design. The combined server entry is present but
  `disabled: true` — enabling it while an owner is alive is refused by the port
  guard, which is invariant 1 doing its job.
- **Cost:** done.

### Lane B — Real Bob custom modes from the same neutral source

Teach `_write_bob` to emit `.bob/custom_modes.yaml` (loadable) in addition to, or
instead of, today's persona YAML. Each qlab role becomes a Bob custom mode whose
`roleDefinition` is the role body, whose instructions are the role's protocol,
and whose permitted tools are **`MCP` only**.

This is the strongest governance story available: the restriction the Claude lane
achieves with `--allowedTools` and `--agent` would be achieved in Bob by the mode's
own tool groups — the same least-privilege boundary, enforced twice, from one
source file. It also retires a fabricated artifact.

- **Disruption:** contained but real. Touches the sync adapter and
  `test_sync_writes_both_adapters` in
  [test_agents.py:208](tests/test_agents.py:208), which byte-compares generated
  output against what is checked in. The workforce is untouched.
- **Blocker:** confirm the real `custom_modes.yaml` key names against a live Bob
  install before writing a generator against them. Guessing a schema would
  reproduce exactly the problem `.bob/personas` already has.
- **Cost:** ~half a day including the test update. **Recommended next step.**

### Lane C — Bob Shell as a second workforce coordinator backend

`bob -p` is non-interactive and streams, so it *could* drive the five governed
roles the way `claude --print` does today.

**Not recommended now, and deliberately not started.** The coordinator in
[claude.py](qlab/tui/claude.py) is 1,125 lines of hard-won process discipline:
stream-JSON parsing, a silence watchdog, full process-tree termination, durable
phase fencing on interrupt. A second backend means a second implementation of
all of it, and a bug there corrupts workflow state rather than merely failing.
This is the one lane that would disrupt the workforce, which is the thing most
worth protecting.

If it is ever taken, the seams are already in place and are named here:

| Seam | File | What attaches |
|---|---|---|
| Executable resolution | [claude.py:221](qlab/tui/claude.py:221) `resolve_claude_executable` | a `resolve_bob_executable` sibling |
| Argv construction | [claude.py:747](qlab/tui/claude.py:747) `build_claude_argv` | a Bob-Shell argv builder; the inline `--mcp-config` becomes `.bob/mcp.json` |
| Stream parsing | [claude.py:681](qlab/tui/claude.py:681) `parse_stream_line` | Bob Shell's event schema → the same `ClaudeEvent` shape |
| Role injection | [claude.py:629](qlab/tui/claude.py:629) `write_session_agents` | session-local custom modes instead of session-local agent files |
| Audit | [model_routing.py:93](qlab/operator/model_routing.py:93) | `backend="bob_shell"` — the column already exists |
| Model tiers | [model_routing.py:40](qlab/operator/model_routing.py:40) `TIER_MODEL` | Bob's model ids per tier; tiers are the architecture, brands are deployment |

### Lane D — Bob as the SDLC partner for qlab itself

`.bob/rules/` carrying the eight invariants, and `.bob/skills/` for the
repeatable maintenance workflows the repo already documents in prose: regenerate
the adapters, restart the owner after changing served code, run the offline
suite, add a catalog entry at the right stage.

This is Bob used for what Bob is actually built for, and it touches the running
desk not at all — rules and skills are read by Bob, never by qlab. It also
directly addresses the invariants most easily broken by an agent working fast:
invariant 5 (regenerate after editing `agents/*.md`) and invariant 8 (restart
the owner) are both "you must remember to do this", which is what a skill is for.

- **Disruption:** zero.
- **Cost:** a few hours. Highest value per unit of risk after Lane A.

## Recommended order

1. **Lane A** — done.
2. **Lane D** — zero-risk, and it makes Bob visibly part of how qlab is built.
3. **Lane B** — after confirming the schema on a live Bob install; retires the
   fabricated persona format and doubles the least-privilege enforcement.
4. **Lane C** — only with a strong reason. The workforce is the crown jewel.

## Open questions

- Exact `.bob/custom_modes.yaml` key names and whether `availableTools` accepts
  the tool-group names (`MCP`, `Read`, …) or per-tool ids. Blocks Lane B.
- Whether a Bob custom mode can restrict to a *subset* of one MCP server's
  tools, or only to the `MCP` group as a whole. If it is the whole group, the
  per-role allowlist must stay enforced server-side — which the owner API
  already does, so this is a documentation matter, not a security hole.
- Bob Shell's non-interactive event schema, needed before Lane C is estimable.
